WAL statistics track the volume of write-ahead log generated by each resource manager and record type. They break every record's size into two components: record data bytes, which carry the actual change delta, and [[subsystems/wal/overview|full-page image (FPI)]] bytes, which snapshot an entire 8 kB page. This split is the key to understanding why WAL volume spikes after a checkpoint and which operations are the dominant contributors.

## Record size decomposition

WAL statistics classify every [[subsystems/wal/wal-records|WAL record]] as either change data or page image data. The record data (`rec_len`) is everything in the record that is not a full-page image — the header, tuple data, and any other payload specific to the operation. The FPI component (`fpi_len`) is the sum of the compressed backup block images attached to the record, one per referenced buffer.

`XLogRecGetLen()` (`xlogstats.c`) produces this split by iterating over the record's block references and accumulating `bimg_len` for every block that carries an image. `XLogRecGetLen()` then derives `rec_len` as the total record length minus the accumulated FPI bytes. The distinction matters, because these two byte counts have different causes. The `full_page_writes` GUC and the checkpoint cycle govern FPI bytes, while the workload alone governs record data bytes.

## Full-page writes and checkpoint amplification

After each checkpoint, `full_page_writes` requires that the first modification to any buffer write a complete copy of that page into the WAL stream before recording the change. This guarantees that partial-page writes during a crash cannot corrupt data when PostgreSQL replays the WAL. The consequence is that the burst of writes immediately following a checkpoint generates disproportionately large WAL: each first-touched page pays an FPI penalty on top of the actual record data.

In a workload that touches many pages, FPI bytes can exceed record data bytes by a large margin. FPI bytes taper off as the workload modifies the same pages repeatedly within a checkpoint interval. Subsequent modifications to an already-imaged page carry no FPI. The ratio of `fpi_len` to `rec_len` in WAL statistics is therefore a useful proxy for how much of the WAL volume is structural overhead rather than application-driven change.

## Statistics structure

The `XLogStats` struct (`xlogstats.h`) holds two parallel arrays of `XLogRecStats` entries, each containing `count`, `rec_len`, and `fpi_len` as `uint64` accumulators:

- `rmgr_stats[RM_MAX_ID + 1]` — one slot per resource manager, indexed by `RmgrId`.
- `record_stats[RM_MAX_ID + 1][MAX_XLINFO_TYPES]` — a finer breakdown by record type within each resource manager. `MAX_XLINFO_TYPES` is 16, matching the 4-bit record-type field in `xl_info`.

`XLogRecStoreStats()` increments both levels atomically for each record. The per-type index is the upper 4 bits of `xl_info` shifted right by 4. Transaction manager (`RM_XACT_ID`) records are a special case: the highest of those 4 bits is an optional flag rather than part of the opcode, so `XLogRecStoreStats()` masks the result to 3 bits (`recid & 0x07`) to fold flagged and unflagged variants of the same operation into a single statistics slot.

In frontend builds (such as [[subsystems/wal/xlog-reader|pg_waldump]]), `XLogStats` also carries `startptr` and `endptr` to record the range of WAL covered by the accumulated statistics. The server conditionally compiles out these fields, to avoid carrying the extra pointers in every server-side statistics context.

## pg_waldump --stats output

`pg_waldump --stats` uses `XLogRecStoreStats()` on every decoded record to populate an `XLogStats` accumulator. It then prints a table grouped by resource manager. Each row shows the record count, total record-data bytes, and total FPI bytes for that resource manager. A second, more granular output shows the same breakdown per record type within each resource manager.

Reading this output to diagnose unexpected WAL volume is straightforward. Rows with a high `fpi_len` indicate resource managers whose pages are frequently first-touched after a checkpoint. Rows with high `rec_len` relative to `fpi_len` point to operations generating large change payloads regardless of checkpoint state. An index-heavy workload typically shows large FPI contributions from the `Btree` or `Hash` resource managers immediately after a checkpoint, while bulk insert workloads will show high `rec_len` in the `Heap` resource manager sustained across the checkpoint boundary.
